# Delegate mode (away)


Relay mode, where every start, wake and answer waits for the owner, is the default and is unchanged. Before leaving, the owner can switch delegate mode on. The hub then decides internal work itself, keeps the teams running, and keeps for the owner only what must be theirs.

**Switching it on and off.** `hh-hub away --until <time> [--mcp-allow <list>] [--remote-allow <hosts>] [--tools <list>] [--peers <names>] [--no-hook]` prints lines for the owner to paste; `hh-hub back` prints the line that ends it. hivehouse never runs `sudo` and never asks for a password: the lines create one file as root, so a changed script cannot capture the password and the owner sees exactly what runs as root.

- **The file.** One file for each user: `/Library/Application Support/hivehouse/delegate.d/<uid>` on macOS, `/etc/hivehouse/delegate.d/<uid>` on Linux, where `<uid>` is the user's real user id as `/usr/bin/id -u` prints it (never `$UID`, `$USER`, an argument or a setting). Several people can share a machine, each with their own hub, and each can be away on their own: one user's file says nothing about another's. Line 1 is `hivehouse-delegate 5`, then `hub=<the hub's folder>`, `until=<epoch seconds>`, `mcp=<list>` (the MCP servers the owner allowed: letters, digits and `_ , . : -`), `hosts=<list>` (the ssh hosts the away sessions may read from), `allow=` (reserved in this release: it must be empty) `tools=<list>` (the extra tools the owner allowed, see below) `peers=<list>` (the sessions on other machines the owner named, see below) and `hook=on` or `hook=off` (line 9, see "Turning the hook off" below); `hosts=`, `tools=` and `peers=` may be empty. The `sudo` lines that `hh-hub away` prints with `--mcp-allow`, `--remote-allow`, `--tools`, `--peers` and `--no-hook` write them (`allow=` is written empty; line 9 is `hook=on` unless `--no-hook` is given). A file written by 0.5.0 (`hivehouse-delegate 1`, exactly the first four lines) is still read, with no hosts, a version 2 file (0.5.1, the first six lines) is still read, with no tools, a version 3 file (0.5.2, the first seven lines) is still read, with no peers, and a version 4 file (0.5.4, the first eight lines) is still read, with the hook on. The `mcp=` list is read from this file, never from `away.json`. The away hook reads it from `HH_AWAY_MCP_ALLOW` in the session's launch environment, copied from the file when the session started, so a narrower list from a later `hh-hub away` applies only to sessions started after it. Delegate mode is on exactly while this file is valid. Valid means: the file, its folder and every folder above it are not links and not writable by group or others; the file and its folder are owned by root; the content is exactly the lines of its version (four for version 1, six for version 2, seven for version 3, eight for version 4, nine for version 5, whose line 9 must be exactly `hook=on` or `hook=off`) and every value is one this release accepts (any word in `allow=`, a bad host name or a tool that is not one of the five below makes the file invalid and away mode stays off); and `until` is in the future. No environment variable or setting changes the path, the owner or the content, and every executable that asks starts with `#!/bin/bash -p` and calls outside commands by absolute path, so a fake `date`, a function or a `BASH_ENV` cannot revive an expired file.
- **The file must belong to the user who reads it.** The hub it names, its `.hivehouse-hub/`, `projects.json` (which homes get bypass) and `hub.json` (which Claude is the hub) must be owned by that user, not links, and not writable by group or others. So must each project's home that is granted bypass: a session working in a folder another user controls would load that user's `CLAUDE.md`, hooks and `.mcp.json`. The files inside a home are not checked one by one, and neither are `tasks.jsonl`, `holds/`, `decisions/` and `away.json` in the hub's folder; `hh-hub` runs with `umask 022` and takes group and others' write off `.hivehouse-hub/` (at `init`, `add`, `remove`, `self` and `away`), which puts those right. A hub or a project home cloned or made under `umask 002` (775) is refused while away until its owner runs `chmod go-w` on it; `hh-hub away` checks all of it first, prints no `sudo` line for an away that would be refused, and prints the reason and the `chmod go-w` line instead. `hh-hub status` shows `away_refused` and its reason when a file exists at the user's path but is refused.
- **Away mode needs a root-owned `jq`.** The away hook and every check that grants away powers read their JSON with the first of `/usr/bin/jq`, `/usr/local/bin/jq` and `/opt/homebrew/bin/jq` whose file and every folder above it are root's, not links and not writable by group or others (`hh_jq_fixed` in `bin/hh-lib.sh`; the hook also fixes its own `PATH` to `/usr/bin:/bin:/usr/sbin:/sbin` first of all). A Homebrew `jq` belongs to the user, so it never passes: the user's own account is exactly the away session being guarded, and a `jq` it could replace could name any hub or project. macOS 15 and later have `/usr/bin/jq`; elsewhere, install one root-owned. With none, the hook denies every call and bypass is refused (fail closed); scripts that decide nothing work as before.
- **Who can read it.** The file is mode 0644, so other users on the machine can read whether you are away and where your hub is. On macOS every user shares the group `staff`, so a group-only mode would protect nothing.
- **At most 7 days.** `until` may be at most 7 days ahead. The hub's heartbeat is a `CronCreate` job: it lives only as long as the hub's session, fires only while the hub is idle, and a recurring one expires after 7 days. After a reboot nothing runs until the owner starts the hub again.
- **Before leaving, two things only the owner can do**: Claude Code shows a one-time warning the first time it runs in bypass mode (`Yes, I accept`; it then writes `skipDangerousModePermissionPrompt` to the user's settings), and a folder-trust dialog for every folder it has not trusted. `hh-hub away` checks both, for the hub's folder and for every folder of every project it lists, and prints what is missing. Claude Code decides trust per folder: a git repository does not inherit it from the folder above, and a worktree is judged by its main repository's entry, so one line covers a repository and its worktrees. `hh-spawn` warns when a worktree it is about to use would stop at that dialog. Nobody can answer these dialogs while the owner is away.
- **The hub starts marked.** The start line `hh-hub away` prints runs the hub in bypass with `HH_AWAY_BYPASS=1`, `HH_PROJECT`, `HH_AWAY_HUB` and `HH_AWAY_MCP_ALLOW` in its launch environment, and with every MCP server Claude Code is configured with (user, project, plugin and claude.ai connectors): no `--strict-mcp-config` or `--mcp-config` is passed, and no `away-mcp.json` is written. The owner exits the running hub first, so two do not share the folder. The hub acts in delegate mode only when `printenv HH_AWAY_BYPASS` prints `1`.
- **`hh-hub away-args`** prints the same start as items, for a tool that starts the hub itself: one item per line, `env NAME=value` for each launch environment variable (`HH_AWAY_BYPASS`, `HH_PROJECT`, `HH_AWAY_HUB`, `HH_AWAY_MCP_ALLOW`, in that order), then `arg <item>` for each claude argument in order. It is the items of the start line after `claude`, built by the same function. It reads the owner's delegate file as it stands, for this user and this hub folder, and exits 4 with a reason when none is valid. Example, for a hub `lead` in `/work` with `mcp=docs`:

  ```
  env HH_AWAY_BYPASS=1
  env HH_PROJECT=/work
  env HH_AWAY_HUB=/work
  env HH_AWAY_MCP_ALLOW=docs
  arg --name
  arg lead
  arg --permission-mode
  arg bypassPermissions
  arg --no-chrome
  arg /hivehouse:hub
  ```

- **Bypass is granted only under three conditions together**: the owner's delegate file is valid and lists the project's home, the caller's own Claude carries the away marker, and the owner's `permission_mode_local` is `auto` (a stricter value, or a project's own tighter setting, keeps a session out of bypass). Bypass is never a value the owner or a project can name. An orchestrator the hub starts or wakes and an agent `hh-spawn` starts get it on those terms. `hh-remote-sync start-agent` never starts bypass; a dedicated host is where the owner may start a bypass session by hand.
- **When it ends** (`hh-hub back`, or the file expires), the hub tells the owner to restart it out of bypass, and until they have, it asks before every start, wake, run or answer, as in relay mode.

**What the hub decides, and what it keeps for the owner.** It decides plans and questions about work inside the project's own repositories and branches, its tests, its agents and their number, worktrees, overnight runs of tasks the owner gave, and wake, start, continue and run for those tasks. It keeps for the owner: a push, a merge, a deploy or migration, anything that sends or publishes outside the machine, a paid step, deleting data that is not the team's own scratch, a change to settings or permissions, a new task, and every screen dialog. A kept item is logged as a question, its task waits, and other tasks go on. `hh-hub hold <project>` keeps the hub away from a project altogether.

While the owner is away the hub never answers a screen dialog (`hh-hub answer` refuses; `hh-hub dialog` still reads it). Its answers go out as `HUB on TASK <id>: <decision>`, never `OWNER on TASK`, so an orchestrator always knows whose words it has. Each decision is recorded, with the question and the answer word for word, in `.hivehouse-hub/decisions/<task id>.md` and a `decided` event (`hh-hub decide`). When the owner is back, the hub opens with what it decided since they left, and the screen keeps "decided while you were away" until the owner presses Seen (`hh-hub status --json` shows `hub.last_away` after away ends).

**Keeping the teams running.** On each beat the hub runs `hh-hub recover --json --max-starts <hub_max_starts_per_day>` and carries out what it prints: wake a stopped orchestrator, or one that ended unregistered but left a transcript (resumable), that has an open task, send an orchestrator `RESPAWN:` for agents that stopped, restart a hung session (below), and list a dialog for the owner. The same action on the same item is tried at most 3 times in 24 hours, then the task is blocked for the owner; and at most `hub_max_starts_per_day` sessions are started or woken in 24 hours, each wake counted as it is decided, so two stopped orchestrators and room for one wake one. That daily cap is a guideline the hub passes, not a guard: the hub runs in bypass and could ignore it. Spend is not tracked here: overnight runs stop at their own ceiling.
**Hung sessions.** A hung session is restarted, never typed into. It counts as hung only on positive evidence: Claude Code's working line (`✳ Effecting… (3s · thinking)`) is recognised, and its elapsed time is the same on every beat for 15 minutes, for the same process. A screen hivehouse does not recognise is "unknown" and is never restarted; a session that is slow but still counting is not hung. The hub then stops that Claude process by its recorded process id and start time, never by name or pattern: it checks again that the process is the recorded one, is Claude, is not the hub's own, runs under the pane whose screen it read, and that the screen still shows the same line; it sends TERM, waits up to 10 seconds, and sends KILL only if it is still the same process. This is the one place hivehouse stops a process it did not start; `rules/RULES.md` names it, and it applies to the hub's recover only, in delegate mode, not to agents. The session is then resumed in its own conversation: an orchestrator by `hh-hub wake`, an agent by `hh-spawn --respawn <agent> --resume`, typed one short line ("You were restarted by hivehouse after your session stopped responding…") instead of the full pickup line. A session is restarted at most 3 times in 24 hours, then its task is blocked for the owner; a hung orchestrator is stopped only while the daily cap leaves room to wake it; a stop that does not take is reported once and not tried again for 24 hours.

**One limit.** A team counts only when it sits in the project's home or in a worktree of the home's own repository that has a `.hivehouse/team.json`. A team in a separate clone of the repository is not seen.

## What away mode guards, and what it does not

**Away mode is not a sandbox.** In bypass, any session can run any command as the owner's user, with the owner's files and credentials. The refusals below stop the actions delegate keeps for the owner; they are not a security boundary, and switching away on means trusting the teams the hub runs.

**Who is guarded: the marker.** A session hivehouse launches in bypass while away carries `HH_AWAY_BYPASS=1` in its launch environment. Every guard keys on it. On macOS, `ps -E` shows no environment for Apple's own programs (bash, sleep) and shows it for others, such as Claude: the marker is read from the Claude process, and a session whose environment cannot be read is refused, never trusted. `ps -E` joins the variables with spaces, so on macOS a marker spelled inside another variable's value (`FOO="x HH_AWAY_BYPASS=1 y"`) counts as set; Linux reads `/proc/<pid>/environ` exactly. A Bash command can unset it for itself, so the hook, not the scripts, is the guard. When a session carries no marker (the owner's own bypass sessions, `dedicated_hosts` runs) nothing here applies. If delegate mode ever has to run in `auto` instead of bypass, there is no marker and no refusals: outward steps are left to the auto classifier and to prompts nobody answers, as in overnight today.

**The hook.** `bin/hh-away-hook` is a `PreToolUse` command hook, wired in `hooks/hooks.json` for Bash, MCP tools, SendMessage, Edit, Write, MultiEdit, NotebookEdit, Artifact, ArtifactData, ArtifactComments, RemoteTrigger and Agent. Without the marker it exits at once. With it, it refuses (exit 2, with a reason the session can read):

- every MCP tool, and the Artifact, ArtifactData, ArtifactComments and RemoteTrigger tools (by their own names), unless the owner's `mcp=` list (`--mcp-allow`; the option `away_mcp_allow`) lists the server (`<server>`) or the single tool (`mcp__<server>__<tool>`). Away sessions start with every configured server; with the hook on, every call to a server not in the list is refused, and the hook is the only limit. Allowing a server allows its write tools too, and a single-tool entry still loads the whole server: only the hook limits it to that tool. This also blocks local tools such as browser automation and the built-in `computer-use` server. A claude.ai connector is named as Claude Code shows it in tool names, and that differs by account (`claude_ai_Image_Gen` on a personal account, `claude_ai_image-gen` on an organisation account): list the form your account shows, or both;
- in Bash: `git` with `push`, `gh` outside its read-only forms, `ssh` (except the reads the owner allowed with `--remote-allow`, below), `scp`, `sftp` and `rsync` to a remote, `curl` and `wget` that upload or use a method other than GET, `npm`, `pnpm` and `yarn` `publish`, `vercel`, `netlify`, `docker push`, `hh-push` and `hh-remote-sync`;
- `claude` run by hand, and `tmux` `new-window`, `split-window`, `new-session`, `respawn-pane`, `respawn-window`, `run-shell`, `if-shell`, `display-popup`, `pipe-pane`, `source-file` and `send-keys`: `hh-spawn` and `hh-hub` start sessions and set the marker again, and SendMessage is the way to talk to a peer;
- Edit, Write and Bash redirects or writing commands (`tee`, `cp`, `mv`, `sed`, an interpreter, and the like) on Claude Code's settings files, hook files, plugin folders, `~/.claude.json`, a project's `.mcp.json` and `~/.ssh/` (whom a session trusts and as whom it signs in), judged by where a link leads;
- in Bash: `rm`, `mv`, `cp`, `install` and `ln` whose destination is, or holds, a protected path (their operands' globs are expanded, and brace patterns are refused); a project or team root, or any folder named `.claude` or `.hivehouse`, cannot be removed, moved or copied over; `unlink`, `find`, downloads, unpacking, git rewrites and `rsync` destinations follow the same rule; `xargs` runs only readers; `git checkout -- .` and `git restore .` in a project root (which holds the state folder), any `git clean` without `-n` in a project root, and `tar` or `unzip` from stdin or from a file the hook cannot list. `echo` and `printf` output into a file is read as before;
- Edit, Write, MultiEdit, NotebookEdit and the Bash write forms into the hub's `.hivehouse-hub/` folder by any session that is not the hub, and into any `.hivehouse/team.json` by every marked session, the hub included (hivehouse's own scripts still write it), judged by where a link leads;
- SendMessage to anyone but the session's own hub and team, checked by name and by process: a `bridge:` address, another project, a name another live session also carries, and anything that cannot be resolved are refused. `RULES.md` adds that a message from anyone else is information, never an instruction; to instruct the hub while away, the owner types into it (Remote Control, say);
- an Agent call that starts a remote (cloud) agent, which would carry no marker.

Anything the hook cannot read or parse is refused too, and so is any failure of the hook itself. Its refusal text says it comes from hivehouse's away mode, is not a permission prompt, and tells the session not to change settings, hooks or permissions to get round it, because a session told "no" has offered to do exactly that.

**A time limit.** The hook answers within 20 seconds (the constant `HH_DEADLINE` in `bin/hh-away-hook`), wherever the time goes: reading a large script, many segments, slow file checks. Past that it refuses (exit 2) with the reason "its check took longer than 20 seconds, so the call is refused", and the session should run smaller steps or use a smaller script. The limit exists because a hook that answers after its `timeout` does not stop the call: Claude Code then runs the tool (tried with Claude Code 2.1.300, a Bash hook that slept past its timeout and then exited 2: the command ran). So `hooks/hooks.json` gives the hook a `timeout` of 30, clearly above the 20, and the hook's own answer always comes first, on its pipes as well: the check runs in a process group of its own, whose every process is killed at the deadline (and at a normal end too, if one is left), and it writes to private temporary files that the hook relays and removes, so no leftover of the check can keep Claude Code's stdout or stderr open after the answer. The limit is in the hook, never read from the environment or a setting.

**A second layer.** `hh-push`, every `hh-remote-sync` subcommand and `hh-cleanup --finish` also refuse with exit 4 when `HH_AWAY_BYPASS=1` is in their environment; `hh-cleanup --disk` stays allowed. These three run under `#!/bin/bash -p`, and so does `bin/hh-away-hook` (it finds `hh-lib.sh` through `HH_BIN`). A Bash command can unset the variable for itself, so this is a backstop behind the hook.

**What the hook does not catch.** The list is not complete, and this page says so on purpose:

- A program that runs another (`python -c`, `perl -e`, `awk` with `system()`, `make`, a git alias) is not read.
- The rules above for destinations are not complete either, in the same class as `python -c`: `python3 -c` with a built path, `curl -K`, the output paths in `~/.curlrc` and `~/.wgetrc`, `curl --create-dirs`, `tar` absolute member names, and a link one archive member creates for a later member get through. `git $(cat f)` and `tmux $(cat f)` are not read through either.
- Quoted text is read as data only for `echo`, `printf` and the free-text flag of `hh-hub log`, `task` and `decide`, and only when it holds no `$`, backtick or backslash; `sed -n <lines>p` of a file passes. Any other quoted text is still read as commands, so a note with `). ` or `; . ` in it elsewhere is refused. A backslash inside a single-quoted `echo` payload is refused too, though it is only text.
- A `$(...)` or a backtick as an argument of a writer command is not refused.
- Code given to `sed`, `perl`, `python`, `node`, `ruby` or `awk` is not read as code, so a write or a command after a `;` or a line break inside it is not checked (`sed`'s `w` and `e` included).
- A path built at run time, or a command computed inside code, is not read.
- The matching is by words, not by structure. `$'\x67'it push`, `g${e}it push` and zsh glob qualifiers (`*(e:'…':)`) get through. A script file the call runs (`bash f`, `sh f`, `zsh f`, `. f`, `source f`, `./f`, behind a wrapper with its arguments such as `timeout 5` or `sudo -u root`, and as the code of `sh -c`) is read first and its text is checked by the same rules, up to four scripts deep. A file that is missing, unreadable, over 256 KB or a link the hook cannot follow is refused, and so is a file the same call writes and then runs (it is not there to read yet). A file that starts with a Mach-O or ELF magic number, or has a NUL byte in its first line, is a program and is not read. The hook refuses what it cannot read first: a shell fed by a pipe (`| bash`), a process substitution (`bash <(...)`), a command substitution given to a shell (`bash -c "$(...)"`), `eval` of a variable or substitution, `xargs` or `find -exec` with a shell, and `BASH_ENV=` or `ENV=` beside a shell. A quoted `push` beside `git`, as in `git commit -m "fix(push): …"`, is refused: rephrase, and `| bash` inside quoted text is refused the same way. Heredoc bodies are data, never commands, only when every command in the whole call (each stage of each pipeline and list, on every line outside a body) is a known reader: `cd`, `cat`, `grep`, `jq`, `wc`, `head`, `tail`, `sort`, `uniq`, `hh-hub task` or `hh-hub decide` (`git` is not one, since `git -c alias.x='!sh' x` runs a program). One other command anywhere (`bash s.sh` on a later line, `eval "$x"`, an unlisted program through a pipe, `hh-slot run`) keeps every body checked as commands, and so does a command substitution (`$(` or a backtick) anywhere in the call, a line that ends in a pipe, `&&` or `||`, or a quote left open at the end of a line; an unquoted body keeps its lines with `$(` or a backtick checked either way.
- A marked session can still reach the network or start an unmarked Claude in ways the hook does not see: `osascript` running `claude`, or a tool that is not on the hook's matcher. `WebSearch` stays allowed, like `curl` GET, and `WebFetch` is allowed only when the owner listed it with `--tools`; both are reads that can carry data out in the address or the query.
- The list of protected files is not complete. In particular, an away session may write the files Claude Code reads as standing instructions: `CLAUDE.md` and `CLAUDE.local.md` in a project, in the hub's folder or in `~/.claude/`, the memory folders, and the skills and commands under `.claude/`. That is how the hub keeps saving the owner's preferences while they are away, and it also means an away agent can leave instructions that later sessions read.
- The hook guards sessions of this plugin. It assumes the owner's `disableAllHooks` is not set.
- Nothing runs while the machine is off. Remote hosts are reached while away only by the reads the owner allowed with `--remote-allow` (`hh-remote-sync` is refused).

## Customising what away mode allows

Away mode allows nothing beyond its fixed rules, and only the owner widens them, in the root-owned delegate file. `hh-hub away` writes it from the options below, as lines for you to paste; hivehouse never runs `sudo`, and no agent, hook, setting or option can add to the file or loosen away mode any other way. An agent that is asked to allow something prints the lines for you to paste, and never edits anything to get round the refusal.

- `--remote-allow <hosts>` (comma-separated real ssh host names, letters, digits, `.`, `_` and `-`, not starting with `-`, or `user@host`) lets the away sessions read from those hosts, and only read. ssh passes as one command of plain words, `ssh -F none [-T] [-o ConnectTimeout=<digits>] [-o BatchMode=yes] <host> <command>`, with the host exactly as listed and `-F none` always there: ssh would otherwise read `~/.ssh/config` and the files it includes, which a session could write to point a listed name somewhere else, so with `-F none` no config is read and names from your `~/.ssh/config` are not usable while away (list the real host name). Any other ssh option, a host that is not listed, a command with no remote command, a variable or substitution for the host, and any quote, backslash, `;`, `&`, `|`, `(`, `)`, `` ` ``, `$`, `<`, `>`, newline, glob character or `~` in the remote part refuse the whole command.
- What the remote command may be: its first word must be one of a read-only list (no `env`, `nohup`, `name=value` prefix or other wrapper in front): `tmux` with `list-panes`, `list-sessions`, `list-windows`, `capture-pane -p` or `display-message -p`; `ls`, `cat`, `head`, `tail` (not following), `grep`, `sed -n` with a `<digits>[,<digits>]p` script only, `wc`, `df`, `ps`; `git log`, `show` and `rev-parse` (`log` and `show` must carry `--no-ext-diff --no-textconv --no-show-signature`, which stop a program named in the remote repository's config from running; `git status` and `git diff` are not allowed, because they can run one too); `hh-context`, `hh-slot status` and `hh-hub tasks`. `hh-hub status` is not on the list: it runs `git status`. Nothing that writes, starts a session or runs another program is on the list, and no option of `hh-hub away` adds a command to it. `~/.ssh/` is protected in away sessions, so a session cannot change `known_hosts` or the keys.
- `--allow` is reserved in this release. The delegate file keeps an `allow=` line, which must be empty: `hh-hub away --allow <anything>` refuses to print (exit 4, "allow= is reserved; no command is allowable in this version"), and a file whose `allow=` holds a word is invalid, so away mode stays off. `scp`, `sftp` and `rsync` to a remote stay refused while away, whatever the file says. Why: a listed `scp`, `rsync` or `sftp` would reach any host (not only the ones in `--remote-allow`), would read `~/.ssh/config` like ssh, and has routes that run a program (`rsync --rsync-path`, `sftp -b`, `scp -O`); and `hh-push`, `hh-remote-sync`, `vercel` or `netlify` as a standing grant of up to 7 days would break "a word given for one run does not carry to the next". Nothing applies to the remote part of an ssh command except the read-only list above. `hh-hub status --json` shows the hosts in force.
- `--tools <list>` (comma-separated, any of `Workflow`, `WebFetch`, `DesignSync`, `ArtifactCheck`, `PushNotification` and `Chrome`, below) is the owner's choice of extra tools for the night, made when switching away mode on (the hub skill asks which). A listed tool passes in an away session; an unlisted one is refused with a message that names `hh-hub away --tools`. Without `--tools` the file gets an empty `tools=` and none of the five tools passes and Chrome is off. The choice is in the root-owned file, so no session can add to it, and a file that names another hub grants nothing. `CronCreate` and `ScheduleWakeup` always pass: the hub's own beat needs them. `hh-hub status --json` shows the tools in force.
- **Chrome** is off for every away session (`--no-chrome`) unless two things hold: the owner's switch and a downward grant. The switch is `hh-hub away --chrome`, which adds the value `Chrome` to the file's `tools=` list (no new line; `--tools` may name it too). No tool is named Chrome, so the switch opens nothing by itself. The grant goes down one step at a time: the hub starts an orchestrator with `hh-hub start <project> <task id> --chrome`, and a session that holds the grant starts an agent with `hh-spawn ... --chrome`. A granted launch gets `HH_AWAY_CHROME=1` in its launch environment and no `--no-chrome`; every other away launch keeps `--no-chrome`. All of these must hold, else the launch is refused (exit 4, with the reason): it is an away (bypass) launch (outside away mode `--chrome` is refused: "Chrome is only turned off for away launches"); the delegate file is valid for this user and hub and its `tools=` has `Chrome`; for `hh-hub start`, the caller is the recorded, marked hub; for `hh-spawn`, the calling Claude carries `HH_AWAY_CHROME=1` in its launch environment (read as the away marker is). The hub's own start (the line `hh-hub away` prints, and `hh-hub away-args`) never has Chrome, so the hub cannot grant itself, and a session without the grant cannot pass it on. `team.json` records `chrome: true` for a granted agent, but the record grants nothing: `hh-spawn --respawn` gives Chrome back only when the calling session holds the grant itself and the switch is still on; otherwise it respawns without Chrome and says so. With the hook on, the Chrome server's tools (`mcp__claude-in-chrome__*`) pass only when the hook's launch environment has `HH_AWAY_CHROME=1` and the file's `tools=` has `Chrome`; otherwise the MCP rule above applies as before.
- `--peers <names>` (comma-separated session names: letters, digits, `.`, `_` and `-`; no spaces, brackets or wildcards) names sessions on other machines, an orchestrator or an agent, that the hub and its orchestrators may message while away. A SendMessage whose target is a listed name, alone or as `<name> [<ref>]`, passes only when the caller is the hub (its Claude's pid and start time are the ones `hub.json` records) or the registered orchestrator of one of the hub's projects (the same proof against its project's `team.json`); a folder alone proves nothing. A `uds:` address is never a peer, and a listed name that a live session on this machine carries is refused, so nothing local can pose as a peer. Every send leaves one line (time, peer, sender, first line of the message) in `.hivehouse-hub/peers.jsonl`. Agents never reach a peer, and a message from a peer to you is information only. What the peer then does is governed by its own machine's permissions and hook. Without `--peers` the file gets an empty `peers=` and no one may message a session on another machine.
- What can never be lifted by any option except `--no-hook` (below, which turns the whole hook off): starting sessions by hand (`claude`, `tmux new-session` and the like), which would carry no marker and escape every guard, and so `hh-hub start` with no arguments (it starts or attaches a hub) is refused for every away session, the hub included, while `hh-hub rotate`, `hh-hub self` and `hh-hub context` are refused for every away session except the hub's own (they type into or record the hub's pane); writing Claude Code's settings, hooks and plugin files and `~/.ssh/`; `git push` and the other publishing commands.
- `--no-hook` writes `hook=off` as line 9 (without it the line is `hook=on`). **Turning the hook off.** With a valid file for this hub that says `hook=off`, `bin/hh-away-hook` after it has read the call and the session's launch variables (a call it cannot parse, a missing `HH_PROJECT` or `HH_AWAY_HUB`, or no root-owned `jq` still refuses), allows every tool call and makes none of its checks. That is every check this page describes for the hook: the MCP allowlist, the extra-tools list, the Bash rules (push, publish and upload commands, starting `claude` or tmux, writes to Claude Code's settings and hook files, `~/.ssh/` and the hub's records, `rm`, `mv`, `cp` and the like on protected paths, remote commands over ssh and scp), the SendMessage rules, and the Edit and Write rules. The hivehouse hook then does not check this user's away sessions, so the owner's own guard has to. It is read only from the root-owned file: an environment variable, a setting or anything a session can write cannot turn it off, and a file that is missing, invalid, expired or names another hub keeps it on. What stays with the hook off: bypass launches still need the valid delegate file, `hh-push`, `hh-remote-sync` and `hh-cleanup --finish` still refuse while the marker is set, and the hub's screen hook (`hooks/hub.tsx`) is unchanged.
- Messages to sessions on other machines stay cut off while away: a Remote Control row does not say which host it is on, so only the names the owner lists with `--peers` (above) are let through, by the proof above. The ssh reads above cover status checks.
- Roles, rules and the brief template are yours to change in `custom/` (see [Customise hivehouse](customise.md#customise-hivehouse)), and nothing in `custom/` can loosen away mode. Note that an away agent can rewrite its own team's, and another project's, future roles and rules in custom/: no grant is loosened (away grants come only from the root-owned delegate file), but you should know. The hub itself is the exception: while the owner is away for its hub, `hh-resolve` (and every other read of a role, the rules, the brief, the pickup line or the handoff template for the hub) gives the plugin's own file and never a custom one, and a delegate file that exists but is refused counts as away, so a text an away agent wrote cannot reach the hub's prompt.

**Which records are trusted, and why.** Only the root-owned delegate file gates bypass and delegate mode. Everything else is writable by the owner's user, so by any of their sessions in bypass, and is trusted only that far: `away.json`, the hub's `tasks.jsonl`, `recovery.jsonl` and `decisions/`, a project's `.hivehouse/settings.json` and `team.json`, and Claude Code's own settings. `hub.json` (which Claude is the hub) and `projects.json` (which folders a project covers, and so which get bypass) are writable by the owner's user, but a marked agent cannot write them through its tools: the hook refuses any write into `.hivehouse-hub/` by a session that is not the hub, and any write to a `team.json` by every marked session, the hub included. Both halves have limits: the hub's own session can still write its folder, and a write the hook's word matching does not recognise gets through, so this is not a security boundary.
